ServiceNow Remote Table Guide

A practical guide to building a live view of external data inside ServiceNow using Remote Tables. Includes a simple Pollinations AI example and a more mainstream MySQL events example.

Summary
A remote table is a schema that lives in ServiceNow, but whose rows are built in memory every time someone opens the list. You write a Definition (script or Flow) that calls an external source, then uses v_table.addRow() to return the results. This guide covers setup, the sys_id requirement, access control, and a real-world MySQL pattern.

1. Create the Remote Table

Application Navigator → System Definition → Remote Tables → Tables → New
  1. Click New.
  2. Label: Pollination AI Simple
  3. Check Remote Table.
  4. Add columns: u_prompt (String), u_response (String). Keep sys_id.
  5. Optionally create a module.

2. Create the Query Definition

Application Navigator → System Definition → Remote Tables → Definitions → New

Paste the Query script. Key points:

  • v_table.addRow(row) is the only way to add a row.
  • v_query.setLastErrorMessage() surfaces errors in the list.
  • row.sys_id = gs.generateGUID() is required even though the row is not stored in the database.
var row = {};
row.sys_id = gs.generateGUID();
row.u_prompt = prompt;
row.u_response = body;
v_table.addRow(row);

3. Showing Sys ID on the List

Sys ID is hidden from the normal Personalize List Columns dialog by design.

Application Navigator → System UI → Lists → open Default view for your table → List Elements → New → Element = sys_id

After saving, run cache.do and refresh the list.

4. Deep Dive

  • Transform data before calling addRow (e.g. round currency).
  • Cooldown — store last call time in a system property to avoid rate limits.
  • Dynamic prompt — read v_query.getParameter("u_prompt") so the user can filter and supply their own question.

5. Access Control

On the table form, Controls tab: check Create access controls and set the role (e.g. u_pollination_ai_simple_user). Users without that role will not see the module or the rows.

6. Mainstream Example: Pulling Events from MySQL

A more typical production pattern is to expose a MySQL table as a REST endpoint, then call it from the Remote Table Definition.

Step A — PHP endpoint (see SampleEvents.php in the repo):

// Returns JSON array of events
// Protect with an API key
// Optional ?since= for incremental

Step B — Remote Table script (simplified):

var rm = new sn_ws.RESTMessageV2();
rm.setEndpoint("https://your-server/SampleEvents.php?key=YOUR_KEY");
rm.setHttpMethod("GET");
var response = rm.execute();
var data = JSON.parse(response.getBody());

for (var i = 0; i < data.length; i++) {
  var row = {};
  row.sys_id = data[i].id;          // reuse external unique key
  row.u_title = data[i].title;
  row.u_location = data[i].location;
  row.u_event_date = data[i].event_date;
  v_table.addRow(row);
}

This pattern is the same as the Pollinations demo, just pointed at your own API.

7. Beyond the Demo

  • Add a free Pollinations key to remove rate limits.
  • Set a TTL on the Definition to cache results.
  • Use the Flow field instead of a script (Washington DC+).
  • Make the table editable if you need write-back.
